COD Reconciliation — Full Lifecycle (v2.1)

Author Albert Date 2026-08-11 Version v2.1 Status Draft

1. Background & Problem

XDOCK handles Cash on Delivery (COD) for two clients: Sayurbox and Zalora. v1 of this PRD treated COD as a single confirmation step: rider delivers, rider hands cash to the hub PIC, done. Two real fraud cases (Hendry Gusman, Rp 609,466; Dwi Febryaansyadi, Rp 3,328,000 — both written off using tribe cash flow) showed that model was incomplete in two specific ways, and this v2 closes both gaps.

Gap 1 — money can go missing before it's even collected. Dwi's case: the rider delivered, collected COD, but never marked the order complete in the app. Nobody noticed until Zalora escalated at H+3. The original PRD only started watching an order once it reached "awaiting confirmation" — by definition, too late for this exact failure mode.

Gap 2 — confirming the rider paid the PIC isn't the same as the PIC paying Finance. The v1 model treated "Confirm COD" as the end of the line. In reality the PIC now personally holds physical cash until they reach a bank — a second custody window with the same risk profile as the first, that had zero visibility or accountability of its own.

Current Situation

Both gaps are now closed structurally. The lifecycle has 4 stages and 8 named statuses: In Delivery (On Track → Needs Attention → Unreachable) catches Dwi's exact pattern before COD is even collected. Awaiting Confirmation (Rider → PIC) and Awaiting Deposit (PIC → Finance) are two separate, equally-scrutinized custody legs — each with its own 24h clock, its own confirmation modal, and its own discrepancy check. Resolved is the only terminal state, and only after both legs are confirmed with proof attached.

Desired Outcome

Every order's location in this chain — who's holding the money, since when, against what expectation — is visible without anyone manually reporting status. Resolution (delivery completing, a rider replying) is detected automatically wherever the underlying data allows it; a human only steps in where judgment is genuinely required — a rider going quiet, a PIC sitting on cash past the deposit window, or a discrepancy at either handoff.

Deliberate MVP call, not an oversight: as of v2, Confirm and WhatsApp buttons are clickable on every row regardless of status — the "gate confirmation until delivery is verified" logic from earlier drafts was removed because the real field workflow isn't fully known yet. This is a live decision, not a placeholder; see §edge-cases.

2. Goals & Success Metrics

Primary Goals

  • Detect a stalled or unreachable delivery before COD is collected, not just after confirmation is overdue
  • Split "money confirmed" into its two real custody legs (Rider → PIC, PIC → Finance), each with its own aging, discrepancy check, and proof of handling
  • Replace manual reporting ("PIC says rider didn't answer") with system-detected signals wherever the data allows it — a 30-minute no-response window, not a human's word
  • Give a PIC one consistent action per situation: WhatsApp the rider, or confirm a handoff — never a form with fields that don't apply to the situation in front of them

Secondary Goals

  • Give Ops & Risk a live map of exactly the riders worth locating (Unreachable / Needs Attention only — not a general fleet tracker)
  • Make every COD row traceable to both the client's own order reference and Dash's internal delivery record, each independently clickable into the back-office

3. Scope

In Scope (MVP)

  • Full 4-stage, 8-status lifecycle: In Delivery (On Track / Needs Attention / Unreachable) → Awaiting Confirmation (Rider→PIC) → Awaiting Deposit (PIC→Finance) → Confirmed
  • WhatsApp-based contact mechanism with a pre-filled template, replacing the earlier Log Contact / Escalate buttons entirely
  • Automatic 30-minute response window per WhatsApp send: silence flips the row to Unreachable with no human report required; "Rider Responded" is the one optional manual override, and recovers Unreachable back to Needs Attention
  • Two independent confirmation modals (Confirm COD, Confirm Deposit), each with settlement/method, amount, discrepancy-note gate, and mandatory proof upload
  • Control Tower map view — live GPS pins for Zalora's Needs Attention / Unreachable riders only; Sayurbox rows show "last synced," explicitly no pin
  • Provider Order ID and Delivery ID as two independently hyperlinked back-office references per row
  • Filter panel (Client, Status, Hub, Owner, amount range, has-discrepancy) synced to the existing Client dropdown and status tabs — not a second, conflicting set of controls
  • Pagination and stage-grouped stat cards, each showing both a count and an Rp total

Out of Scope

  • Ops & Risk PIC negligence investigation criteria — still case-by-case by design, not touched by this build
  • Finance Historical write-off sizing beyond the known cases — separate workstream
  • Deferred Legal review of the rider salary-deduction clause
  • Cost WhatsApp Business API / automated sending — this PRD uses a manual template pre-fill a PIC sends themselves, specifically because the automated API was ruled out on cost; see §edge-cases
  • Future Slack-based tiered escalation to Ops Lead (routine ping vs. 🚨-tagged escalate-tier vs. auto-escalation) — agreed in principle, not represented in this mockup's UI since it's a notification/integration behavior, not a screen

6. Screen Specifications

List View — "COD Reconciliation"

Default view. Seen by Ops Staff/PIC, Ops Lead, Ops & Risk, Finance.

Layout

  • List / Control Tower toggle, top of page
  • Time range: 1d / 7d / 30d / 90d tabs, a dedicated Today shortcut (kept in sync with the 1d tab), and Custom Range
  • Stat cards grouped into 4 labeled stage clusters (Total, In Delivery, Awaiting Confirmation, Awaiting Deposit, Resolved) — each card shows both a count and an Rp total, and is clickable as a shortcut into that status's filtered view
  • Status tabs — one per status, 1:1 with the stat cards, no combined/rollup tabs
  • Search (rider name / mitra code) and a Filter panel (Hub, Owner, Amount range, has-discrepancy) — synced to, not duplicating, the Client dropdown and status tabs
  • Table columns (13, horizontally scrollable — the row no longer fits any reasonable screen width): Rider, Provider Order ID (hyperlinked), Delivery ID (hyperlinked), Client / Hub (merged into one stacked cell — client badge on top, hub as a muted sub-line), Owner, Time in Status, Expected, Amount, In Delivery / Confirmation (Rider→PIC) / Deposit (PIC→Finance) / Resolved (the single old Status column split into 4 stage-specific columns — a row's pill appears in exactly one of the four, the rest show a dash, so scanning becomes "which column has color" instead of parsing 8 possible pill texts), Actions
  • Edit Columns: show/hide any column except Rider and Actions, which are locked (hiding either breaks the row's basic usability). Hidden state survives sorting, filtering, and search — it's part of view state, not a one-time render.
  • Pagination: "Showing X–Y of Z", numbered page buttons with First/Last, Show N/page (10/20/30/40/50)
  • Empty state: "No orders match this filter."

Control Tower — At-Risk Riders (map view)

Rider-side accountability only: In Delivery and Confirmation stage (needs_attention, unreachable, outstanding, escalated). Deposit and Resolved are excluded — that's PIC-to-Finance, and the rider isn't part of it anymore.

Layout

  • Map pane: pins for Stage 1 (In Delivery) + Zalora rows only — the combination where live GPS exists and location is actually the thing blocking progress. Stage 2 rows never get a pin, even Zalora ones: delivery is done, so the rider's location no longer changes what happens next. Sayurbox never gets a pin at any stage — no live signal to place one from.
  • Side list: one card per at-risk rider (both stages, mixed together). Card sections, top to bottom: name/code + live-or-stale tag (Stage 1) or "Delivery complete" (Stage 2); status pill + elapsed time; hub; a labeled 2-column ID grid (Provider Order ID, Delivery ID — both independently hyperlinked to the back-office); amount; a bordered action row.
  • Action row differs by stage: Stage 1 shows Center on Map (primary button — Sayurbox shows disabled "No Live Pin" instead) + WhatsApp (WhatsApp (retry) for unreachable). Stage 2 shows Confirm + WhatsApp — both active, no disabled placeholder.
  • Panel height fills remaining viewport space rather than a fixed pixel height, so the map/list area grows on taller screens instead of leaving dead space below a fixed-size box.
  • Clicking a card or its pin selects both in sync (highlight + scroll-into-view); clicking an ID link inside a card opens the back-office without triggering card selection
Open question: should this live inside the existing back office or as a separate dashboard? Not decided here — flagged for Aldi.

8. Edge Cases

No status-based gating on WhatsApp (deliberate) — Confirm is now the exception, not the rule

WhatsApp stays clickable on every row regardless of status, by the same original reasoning: the real field workflow for contacting a rider isn't confirmed yet, so this stays flexible until Ops validates it. Confirm no longer follows that rule. It's disabled on on_track, needs_attention, and unreachable — see the fixed Category D entry in §status-flow for why. The distinction that made this the right call: WhatsApp's gating was a genuine unknown about field workflow; Confirm's was a fact (a delivery that hasn't completed has nothing to confirm), not a policy guess — so it didn't get the same benefit of the doubt. Confirmed rows remain Detail-only — that exception still stands, unrelated to this change.

Fixed, not just decided: Confirm is disabled — no click handler attached at all, not merely styled to look inactive — on on_track, needs_attention, and unreachable, with a tooltip explaining why. Option A from the earlier draft (block it) is what shipped; Option B (reinterpret a Stage-1 click as "delivery done too") is no longer applicable, since there's no click left to reinterpret. Full transition table in §status-flow, Category D — now struck through there as closed.

No path exists for a confirmed fraud case stuck in Stage 1 — proposed, not built

The Confirm fix above closes a bug, but it also closes the one (incorrect) way a PIC could previously get a known-fraud Unreachable row into any tracked flow at all. If Ops & Risk independently verifies — outside the app, since the app will never show completion when the rider is the one withholding that signal on purpose — that a delivery happened and the rider kept the cash, there is currently no mechanism to record that. This is a different problem from the bug just fixed: that was the system being wrong about a delivery's state; this is a human being right about it despite the system never being able to confirm it on its own.

Proposed mechanism, not yet implemented in the mockup: a new action — "Escalate as Suspected Fraud" — visible only on unreachable rows (not needs_attention, which is still too early to presume bad faith), restricted to Ops & Risk per the permission matrix in §roles, requiring a written justification, and routing into the existing Confirm modal pre-set to the Tribe Write-off settlement source that's been in this PRD since v1 for exactly this scenario (Hendry Gusman, Dwi Febryaansyadi). Reuses the existing accountability trail rather than forking a parallel one.

Open tension, not resolved here: this is a manual override on the exact mechanism (auto-detected completion, no human claiming "it's done" on the rider's behalf) that this whole project was built to remove. Narrow and well-gated, that's a legitimate exception; loosely gated, it's the original vulnerability again with extra steps. Undecided: does this need a second approver (e.g. Finance sign-off before the write-off posts), or is Ops & Risk's own investigation sufficient authority by itself?

Two placeholder thresholds, not yet validated with Ops

The 30-minute WhatsApp response window and the 24-hour deposit window (Stage 3) are both reused from the existing 24h confirmation pattern for consistency, not derived from a real number. Both need sign-off before this is a real spec — the deposit window in particular has no basis yet for how long a PIC should reasonably take to reach a bank.

Rider Responded notes are optional, arguably shouldn't be

The stated purpose of this field is "so we know what the issue was" — but it doesn't block submission if left blank (defaults to "No details given"). This mirrors the same non-blocking philosophy applied everywhere else, but is a real tension worth resolving explicitly rather than by default.

Provider Order ID format is unconfirmed for Sayurbox

Zalora's format (ZDE + 9 digits + dash + 4 digits) is grounded in real data seen in the actual Zalora runsheet. Sayurbox's equivalent (SBX-2026-NNNNNN in this build) is an invented placeholder — no real example exists anywhere in this project yet.

Multi-slot / multi-hub riders

A rider can work multiple slots or hubs in a day. If shift/PIC changes mid-day, who is the named owner for that rider's outstanding rows? Owner: Ops — not decided here.

Bulk PIC transfer attribution

A PIC sometimes deposits one bulk bank transfer covering several riders' COD at once. The Confirm Deposit modal assumes a 1:1 rider-to-deposit match; bulk transfers require manual attribution outside this flow for now. Owner: Yogi / Aldi.

No PIC negligence investigation criteria exists yet: the Escalate path in earlier drafts assumed an Ops & Risk investigation process that is, in practice, still case-by-case with no defined criteria or approval threshold. This PRD's Confirm Deposit / discrepancy capture builds the data trail; it does not create the missing governance process around it.

WhatsApp is a manual template, not an integration

There is no WhatsApp Business API here — cost was the explicit reason this was ruled out earlier in scoping. The "Message via WhatsApp" modal pre-fills a template for a human to send themselves; nothing is sent automatically. If this assumption changes, the 30-minute timeout mechanic (which currently relies on nothing but elapsed time, since there's no delivery-receipt signal from an actual API) may need to be revisited.

12. Implementation Notes

The 30-minute window is a server-side timeout, not a client-side one

wa_deadline must be checked by a scheduled job on the backend — never by relying on someone's browser tab staying open. The mockup's live countdown is a UI convenience; the actual status transition to unreachable has to fire independent of anyone watching the screen.

Discrepancy baseline differs by leg — don't reuse one field

Leg 1 (Rider → PIC) checks the confirmed amount against cod_ledger.amount_expected. Leg 2 (PIC → Finance) checks the deposited amount against Leg 1's confirmed amount — not the original expected amount. A rider under-delivering and a PIC under-depositing are two different failure modes and need two different baselines, or a real discrepancy at one leg could get silently absorbed into rounding against the wrong number.

Settlement source / deposit proof are hard gates, enforced server-side

Neither confirmation endpoint should accept a submission missing its required proof file or a required discrepancy note — this needs enforcement in the backend guard, not just hidden/shown in the frontend, the same principle already applied to the original Confirm flow in v1.

Client and Status filters must write to shared state, not duplicate it

The Filter panel's Client and Status fields aren't independent — they read from, and write back to, the exact same state as the top-level Client dropdown and status tabs. If implemented as separate state, the two controls can silently contradict each other (panel says Sayurbox, dropdown still shows Zalora) with no error, just a query that returns nothing. Whatever wraps this in the real API layer needs the same discipline: one filter state, multiple entry points to set it.
