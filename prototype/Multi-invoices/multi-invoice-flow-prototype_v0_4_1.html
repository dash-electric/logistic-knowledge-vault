Multi-Invoice Document Flow

Dua track tetap: Track A, pengiriman hari ini dalam format baru, di mana satu dokumen fisik memuat beberapa invoice dan cukup 1 foto untuk semuanya; dan Track B, invoice "hutang" tertinggal dari kunjungan sebelumnya dalam format lama, yang tidak pernah masuk AI scan di rider app sama sekali.

1. Dua track

Dua track, bukan satu dokumen berhalaman-halaman

Setiap outlet visit sekarang bisa punya dua jenis invoice yang berjalan lewat mekanisme berbeda sama sekali.

Terminologi kunci

5. Full status transition matrix

Ini yang paling penting untuk engineer

Setiap trigger dipetakan ke internal Ops platform dan client webhook. 7-status enum tidak berubah — tidak perlu schema change.

# Trigger From → To Actor Effect di Ops Tab Effect di Rider App (hutang) Webhook ke Client
1 Batch dispatched (new)→pending System Pending +1 Hutang +1 —
2 Rider AI-scan → PASS (new format doc, semua invoice dalam 1 foto) pending→rider Rider App Pending −N, Received by Rider +N Hutang −N (invoice sudah dipegang rider) —
3 Rider AI-scan → FAIL, tap "Foto Ulang" pending→pending Rider App no change no change —
4a Belum siap + foto bukti (GPS) berhasil NEW v0.3 pending→exception Rider App Pending −N, Exception +N Hutang tetap, evidence_id terlampir —
4b Belum siap tapi kamera/GPS gagal NEW v0.3 pending→exception Rider App Pending −N, Exception +N Hutang tetap, reason = LEFT_AT_OUTLET_NO_EVIDENCE → auto-flag review manual —
4c Fallback "Tinggalkan" dari AI gagal berkali-kali (fisik ada di tangan rider) pending→exception Rider App Pending −N, Exception +N Hutang tetap — bukti = dokumen fisik dibawa ke hub —
5 Korlap scan di hub (new format, rider bawa lembar setelah AI scan) rider→await Hub Ops Received by Rider −N, Awaiting confirm +N Hutang no change (sudah 0 sejak step 2) ✓ AWAITING_CONFIRM
6 Korlap scan di hub (old format leftover, rider bawa fisik tanpa AI) pending / exception→await Hub Ops Pending/Exception −1, Awaiting confirm +1 Hutang −1 (untuk outlet asal) ✓ AWAITING_CONFIRM
7 Client acknowledge di Dash Link await→resolved Client (Link) Awaiting −1, Resolved +1 — ✓ RESOLVED
8 Client dispute di Dash Link await→disputed Client (Link) Awaiting −1, Disputed +1 — ✓ DISPUTED
Trigger #2 (rider AI scan PASS): satu event AI PASS untuk 1 dokumen → N invoice sekaligus berubah state. Backend perlu handle sebagai atomic batch transition, bukan N event terpisah. Perlu idempotency_key di request — double-tap atau retry tidak menghasilkan N state changes.
Trigger #4a/4b/4c: dipecah karena tiap jalur punya "bukti" yang beda sifatnya — 4a punya foto+GPS, 4b tidak punya bukti (butuh review manual), 4c sudah punya bukti fisik (dokumen dibawa ke hub). Exception queue ops sebaiknya sort: 4b (NO_EVIDENCE) di atas, kemudian 4a FLAGGED, kemudian 4a evidence lengkap.
Foto bukti (trigger 4a): tidak melalui AI pipeline. Disimpan sebagai raw file dengan metadata lokasi. Rider boleh foto counter/pintu masuk ATAU kertas dokumen kosong — keduanya diterima. Yang tidak boleh: foto dokumen berisi data sensitif outlet lain.

6. Impact analysis per platform

Apa yang berubah — dan yang sengaja tidak berubah

Rider App

Paling banyak berubah
  • Screen redesign: Outlet arrival hub. Badge "Belum Difoto · N" (v0.4). Empty state Track-A-only dan Track-B-only.
  • Screen redesign: Kamera. Viewfinder langsung aktif, shutter = CTA primer, "Outlet belum siap?" sebagai secondary button — tidak ada pre-flight overlay lagi.
  • Screen baru: Bottom sheet alasan (02a). Progressive disclosure — muncul hanya setelah rider tap secondary button.
  • Screen baru: Bukti Kunjungan (E2). Kamera mentah + GPS tag + progress indicator. Foto boleh ke counter ATAU ke kertas dokumen kosong. Copy diperbarui (v0.4).
  • GPS loading state (E2·GPS). Tidak pernah block rider.
  • Frame 07 copy diperjelas. "Kirim Nanti" sekarang menjelaskan efek hutang counter in-screen.
  • Butuh location permission baru (iOS: one-time / Android: while using app). Perlu consent copy.

Ops Platform

Internal — perubahan minimal
  • 7-status enum tetap — no schema change.
  • Exception reasons enum: tambah AI_FAIL_MULTIPLE_RETRY, PREFLIGHT_NOT_READY_STEMPEL, PREFLIGHT_NOT_READY_TTD, LEFT_AT_OUTLET_NO_EVIDENCE.
  • Exception detail view: butuh evidence viewer — foto bukti + pin GPS di map + jarak dari koordinat outlet terdaftar. Sort queue: NO_EVIDENCE → FLAGGED → evidence lengkap.
  • Audit log field baru: photo_subject (COUNTER / EMPTY_DOCUMENT) untuk setiap exception record.
  • Tidak berubah: scan hub UI, status transitions dari hub scan.

Dash Link (Client)

No change needed
  • Webhook events tetap: AWAITING_CONFIRM, DISPUTED, RESOLVED.
  • Client tidak tahu invoice di-AI-scan (Track A) atau di-korlap-scan (Track B).
  • Efek samping positif: kualitas invoice yang reach AWAITING_CONFIRM lebih tinggi → client dispute rate diperkirakan turun.
