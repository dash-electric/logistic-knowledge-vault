UJP Native Design

Port Usulan Jasa Pengangkutan (the per-trip running-cost request that authorizes a driver's uang jalan) from the Supabase app logisticdash into the logistics console. The approve step creates the DIRECT_4W shipment in the same transaction, so "forward to dispatch" stops being an integration and becomes a write.

Targets: react-logistic-web + nest-logistic-serviceSource: winggarahmanda-bit/logisticdashReviews: eng CLEAR · design CLEAROwner: yogi.ermanto@dashelectric.co
What ships
A ujp module (create, estimate, list, detail, approve/reject/cancel) and a console UI: queue list, 5-step wizard, approval panel. Approve writes the shipment, route and stops through the existing 4W writer.
What changes hands
Money math, reference numbering, side-effects and authorization move from the browser to the server. The browser only collects inputs and asks /estimate what they cost.
What is deliberately out
Google Sheet mirror, Basecamp forward, schedule auto-create, combine, revert, edit-after-submit, ring tariff, route-plan master, subcon vendor master. Each has a reason in §11.

01The key move

In the old app the browser was the orchestrator: it computed totals, picked a random reference number, inserted the row under row-level security, created a schedule, mirrored a Google Sheet, and on approve called Basecamp and the old two-wheel dispatch API. Every one of those was a separate way to drift. In the new stack the shipment is the dispatch and the route is the schedule, so most of that scaffolding has nothing left to do.

02Components

The frontend owns presentation and input. The ujp module owns the entity, numbering, money and authorization. Shipment creation stays in the shipment module, reached through a shared domain service extracted from the existing 4W use case, because the repo rule is "share repositories and services, never another module's use case".

03Data model

One request table with typed columns, an append-only history, a daily counter for numbering, a small vehicle master, and one new column on shipments. Lanes and reasons are read from tables that already exist and are not changed. Money columns are numeric(14,2) handled as strings through MoneyHelper; never floats.

04Lifecycle

05Approve transaction

External reads happen before the transaction so no row lock is held across a network call. Inside the transaction the shared creation service writes shipment, status history, route, stops and links, then the UJP row gets its shipment_id. Any throw rolls everything back and the request stays SUBMITTED.

06Money

The formula is ported from the old app's ujp-calculations.ts plus the subcon branch that lived in its form. It exists once, in UjpCostService. The browser calls POST /v1/ujp/estimate (debounced, aborting stale requests, sequence-checked) for the live preview; create recomputes from raw inputs and ignores any client-sent totals. The reconciliation oracle is a fixture of 30 real UJPs run through the old code with its half-up rounding reproduced.

totalKmWithMargin = kmYangDiajukan / 0.95                     # 5% buffer
estimasiBbmLiter  = baseline > 0 ? round1(totalKmWithMargin / baseline) : 0   # EV: baseline = 1 / konsumsiPerKm
computedBbmCost   = round(estimasiBbmLiter × energyPrice)
totalBbmCost      = bbmFixOverride ?? computedBbmCost

flazz  = totalBbmCost + tollFlazz + parkirTapMachine
manual = parkirManual + biayaBongkarMuat + biayaLainLain + uangMakan

if payee == subcon:              Flazz = 0        Transfer = nominalTransfer
elif eMoney.trim().lower == "no": Flazz = 0        Transfer = flazz + manual
else:                            Flazz = flazz    Transfer = manual
estimatedAmount = Flazz + Transfer
The reference number is server-authoritative: ujp_daily_counters is upserted atomically inside the create transaction, giving finance gap-free daily numbering in the format they already reconcile against. The old app used a random 4-digit suffix with no unique constraint.

08Security and trust

  • Approver gate is server-side. UJP_APPROVER_EMAILS (Joi-validated, lower-cased) is checked against the JWT email, which the core service puts in every web user token. A missing claim or an empty list fails closed. The requester can never approve their own request. The frontend reads a mirror of the list only to hide buttons.
  • Read-side masking. Anyone who is neither an allowlisted approver nor the requester sees the account number as •••• 1234 and the nominal as "Disembunyikan". Enforced in the response mapper, so no client change can leak it.
  • Money is never trusted from the client. Totals in the payload are ignored; the server recomputes.
  • Audit. Every transition writes ujp_status_history with actor email, from/to, reason code and note.

09Scale and performance

  • List: a STORED search_text column (reference, client, driver, plate, origin, destination) under a trigram GIN index; composite indexes on (status, created_at DESC), (client_id, delivery_date), (delivery_date); page/limit with limit ≤ 200. The old app pulled every row and paginated in the browser, silently capped at 1,000.
  • Estimate: one debounced call per input burst; previous request aborted; responses with a stale sequence discarded; the Review step recheck is the last word before submit.
  • Approve: external reads pre-transaction; the row lock is held only for local writes.
  • Numbering: one atomic upsert on today's counter row; no retry loop; contention limited to one row per day.

Out of scope, with reasons

  • Google Sheet mirror: the native list and detail replace it; revisit only if finance asks after a month.
  • Basecamp spend-control forward: separate integration with its own credentials.
  • Schedule auto-create: the route created on approve is the schedule.
  • Combine, revert, edit-after-submit: multi-drop stops, shipment cancellation, and cancel-plus-resubmit cover them with an honest audit trail.
  • Ring / PER_RING tariff: billing-side, no tariff tables here.
  • Route-plan master and per-lane cost presets: lanes come from addresses; presets are a follow-up once typos are observed.
  • Admin UI for vehicles, JWT role for approvers, historical import from logisticdash, CSV-import retirement: recorded as TODO-20 to TODO-26.
