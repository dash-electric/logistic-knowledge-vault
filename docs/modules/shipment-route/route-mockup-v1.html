What this mockup asks the specs to change

Three deltas against the current drafts. None are settled — each needs a product call before implementation.

  1. Per-stop workflow selection instead of pure auto-resolution. workflow-prd-trd v1 Req 3 resolves a stop's workflow from the client's single ACTIVE definition matching the stop type, with no caller input. This flow keeps that resolution as the default but lets the planner override it, which needs a nullable workflowID on the stop payload for POST /internal/v1/routes and POST /internal/v1/routes/:routeID/stops, plus validation that the chosen workflow's stopType matches the stop and its client is on the stop.
  2. More than one ACTIVE workflow per client and stop type. stop_workflows carries a partial unique index of one ACTIVE per (client_id, stop_type). A picker with one option is not a picker — offering a genuine choice (standard vs cold chain, say) means dropping that index and deciding what "the default" means when nobody picks.
  3. Shipment-level type. shipment_type lives on routes today (route-prd-trd v1 Req 14, and its open question "Shipment-level typing"). This flow sets the type on the shipment and lets the route inherit it, which implies a shipments.shipment_type column and a rule for what happens when one route serves shipments of mixed types.
