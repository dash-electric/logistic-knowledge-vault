    Assessment: model okupansi eFishery → Dash
    
    
    Dibaca dari be-warehouse-management-system (service storagecapacity, view storage_sku_capacity_view) dan dashboard Storage Capacity di monorepo-frontend-upstream-ops.
    

    
    
      
    
        
    Yang dipakai eFishery
    
        
      
          
    • Kapasitas per SKU per warehouse (warehouse_stock_capacity.quantity_capacity): "1 bin muat N unit SKU ini". Diisi lewat import CSV (product_external_id, product_name, uom, quantity_capacity).
      • 
          
    • Okupansi bin = on-hand SKU di bin ÷ quantity_capacity. Status: TERSEDIA (kosong), TERISI (>0%), HAMPIR_PENUH (>50%), PENUH (>80%), KAPASITAS_SKU_BELUM_DIATUR (ada stok, kapasitas belum diset).
      • 
          
    • Occupancy board per warehouse: bin terpakai ÷ total bin, dirinci per section (rack/floor), kartu progress bar + tabel list per SKU dengan filter lokasi/section/bin/status, export CSV.
      • 
          
    • Section punya tipe RACK / FLOOR; bin di-generate massal dengan kode urut.
      • 
        
    
      
    
      
    
        
    Keterbatasannya buat logistik Dash
    
        
      
          
    • Satu bin dianggap milik satu SKU; bin campur (beberapa SKU/batch) tidak bisa dihitung persennya.
      • 
          
    • Kapasitas berbasis jumlah, bukan ruang: tidak tahu CBM/berat, jadi tidak bisa menjawab "masih muat berapa kubik".
      • 
          
    • Tidak ada koordinat/dimensi storage, jadi tidak ada denah. Tidak ada riwayat okupansi dari waktu ke waktu.
      • 
          
    • Status mengikuti SKU — bin dengan stok tapi SKU-nya belum diset kapasitas jatuh ke "belum diatur", sering terjadi saat katalog baru.
      • 
        
    
      
    
    
    

    
    Yang sudah dipunya Dash dan tidak perlu dibangun ulang: SKU sudah punya weightKg, lengthCm/widthCm/heightCm → cbmPerUnit; stok tersimpan per storage per batch (wh_stocks) di level apa pun pohon Location → Section → Bin; roll-up on-hand per subtree sudah ada di list storage (withStock). Jadi okupansi volume bisa dihitung tanpa tabel kapasitas per SKU.
    

    
    Usulan model untuk Dash
    
    
    
      
    BagianUsulanCatatan
    
      
        
    Kapasitas storageKolom di wh_storages: capacity_cbm, capacity_kg, capacity_qty (semua nullable), plus dimensi fisik width_cm × depth_cm × height_cm (CBM bisa diturunkan).Diset di bin (atau section FLOOR). Null = belum diset → status "belum diset" seperti eFishery, tapi per storage bukan per SKU.
    
        
    OkupansiView/materialized: per storage, used_cbm = Σ qty × cbmPerUnit, used_kg, used_qty; persen = used ÷ capacity. Roll-up ke section/location pakai path <@ yang sudah ada.Bin campur SKU otomatis benar karena satuannya CBM. Mode qty tetap tersedia untuk SKU seragam.
    
        
    StatusAmbang sama dengan eFishery supaya ops familiar: >0 Terisi, >50 Hampir penuh, >80 Penuh; tambah Over >100 (ops menaruh melebihi kapasitas tercatat).Ambang disimpan sebagai konstanta, bukan hardcode di SQL.
    
        
    DenahTabel wh_storage_layouts (1 baris per storage yang ditempatkan): storage_id, x, y, rotation, shape (RACK/FLOOR), levels/rows, cell_cm, cm relatif ke origin location. Pohon storage dan bin tetap dari wh_storages; peta hanya menata bin yang sudah ada (rak: kolom = bin ÷ level).Yang digambar di mockup ini. Section tanpa baris layout masuk tray "belum ditempatkan"; menambah/menghapus bin tetap lewat menu Storage.
    
        
    Rekomendasi put-awaySaat goods receipt, usulkan bin default = bin aktif tipe Storage dengan sisa kapasitas cukup, terdekat ke staging (jarak dari layout).Fase 3; hari ini default bin = bin pertama.
    
        
    PeringatanKPI "Penuh / hampir penuh" di Stock dashboard + Slack alert saat okupansi hub > 85%.Pakai jalur alert Slack yang sudah ada.
    
          
    
    

    
    Tahapan
    
    
    
      
    Fase 1 · 1 minggu
    Kapasitas + okupansi
    • Kolom kapasitas & dimensi di storage (edit storage sudah ada).
    • View okupansi + endpoint GET /storages/occupancy (hub, per section, per bin).
    • Kolom Okupansi % + status di list Storage; KPI di Stock.
    
      
    Fase 2 · 1–2 minggu
    Denah 2D
    • Tabel layout + editor posisi/ukuran rak (drag, snap ke grid 50 cm).
    • Halaman Peta gudang seperti mockup: zoom/pan, warna okupansi, inspector bin, filter client.
    • Export PNG/PDF lembar denah.
    
      
    Fase 3
    Operasional
    • Saran bin saat put-away & picking walk order dari koordinat.
    • Riwayat okupansi harian (snapshot) → tren per hub.
    • Alert okupansi tinggi.
