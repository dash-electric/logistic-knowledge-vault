What changes to build this — BE / Link (not part of the UI)
  1. LinkWebhooks tab gets a sub-nav Endpoints | Webhook list. Endpoints: render WebhooksSection twice with a topic prop (SHIPMENT | OUTBOUND_ORDER) — title, description, event chips and the endpoint list filtered by topic; AddWebhookEndpointModal takes the topic (fixed by the section) and shows that topic's events. Webhook list: one row per shipment / order (grouped by AWB + bookingId, or order code + externalID) showing the latest status and that event's delivery; segmented topic, filters env / webhook status / date, filter box by AWB / booking ID; row expands to the event history + the latest payload (reuse DeliveryStatusPill and JsonBlock from sandbox/sandboxUi). Retry now only on the row's latest event when it is Failed / Gave up (older failed events show “superseded — not retryable”); Retry all failed in the banner; Send now when the latest was Skipped for lack of an endpoint. API docs: nav group “Outbound order” + “Order webhooks”. Sandbox: an outbound-order detail with the same WebhookDeliveriesPanel (simulator for orders is a later step).
  2. BE — existsEndpoint management (/v1/integration/webhook-endpoints), one-time secret, per-environment wall, outbox delivery with retries, GET …/shipments/:id/webhook-deliveries (per shipment, count + last error only).
  3. BE — newwebhook_endpoints.topic (text, default SHIPMENT; enum in TS only) — unique active per (client, environment, topic); the list/create API takes topic. Existing rows backfill to SHIPMENT, so nothing changes for current partners.
  4. BE — newOutbound order events through the same outbox: ORDER_STATUS_CHANGED on OPEN, PREPARING, READY_TO_PICKUP, SHIPPED (with fulfillment.waybill), CANCELLED; sequence per order; fan-out only to OUTBOUND_ORDER endpoints of the order's environment. This reverses PRD/TRD key decision no. 3 (“no warehouse-status webhook”) — update the doc once this mock is approved.
  5. BE — newWebhook list: GET /v1/integration/webhooks?topic&environment&webhookStatus&q&from&to&page&limit (JWT, client-scoped) — one row per shipment / order: reference, latest status, the latest event and its delivery (status, http code, attempts, lastError, nextRetryAt), endpoint. GET /v1/integration/webhooks/:topic/:refId/events — history. POST /v1/integration/webhooks/:topic/:refId/retry — re-queues only the latest event (same event.id) to the endpoint active now; 409 when the latest is already delivered or in flight; POST …/retry-all-failed?topic&environment. When a newer event is enqueued, still-failing older deliveries of the same ref are closed as SKIPPED (reason SUPERSEDED) so the queue never resends stale state. Per-attempt log webhook_delivery_attempts (http code, latency, error, at) — today only a count + lastError. Retention 30 days.
  6. DecideSingle endpoint for both topics (one URL, both bodies)? This mock assumes separate endpoints — simpler to route and to rotate secrets independently.
  7. DecideRetry self-serve for the client (this mock) or ops-only? And is 30-day retention enough — Sandbox could be shorter (7 days).
